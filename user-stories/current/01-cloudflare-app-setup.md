## Implementation Plan

Turn the repo root into a TypeScript project: React Router 8 in framework mode on a Cloudflare Worker (server rendering, little client JavaScript), Postgres through Drizzle, and a test suite that CI runs on every push. The old static site moves into `legacy/` and keeps deploying to the existing `ashlanddailyhelp` Worker until `17-domain-cutover`; the new app deploys to its own Worker, `ashlanddailyhelp-app`, once a production database is configured.

### Choices

- Framework: React Router 8 (framework mode) with `@cloudflare/vite-plugin`. One Worker serves pages, resource routes (JSON, health) and, later, the scheduled feed ingest.
- Database: Postgres with Drizzle ORM. In the Worker, `postgres` (postgres.js) connects through a Hyperdrive binding when one is configured, otherwise through a `DATABASE_URL` secret. Migrations are SQL files generated by `drizzle-kit` in `db/migrations/`.
- Production Postgres host: Neon (serverless, works with Hyperdrive). Provisioning needs an account, so it is a setup step in the README, not code.
- Tests: Vitest. Integration tests run against PGlite (real Postgres compiled to WebAssembly, as the steward does), so they need no server. React component tests use Testing Library with happy-dom. Playwright drives end-to-end journeys against the built Worker and a local Postgres.
- Lint and format: Biome. Type checks: `tsc` (TypeScript 7) in strict mode.

### Steps

1. `git mv` the static site into `legacy/` (`index.html`, the CSS, `app.js`, `core.js`, `data.js`, `sw.js`, `manifest.webmanifest`, `icon.svg`, `robots.txt`, `build.json`, `fonts/`, `art/`, `worker.js`, `wrangler.jsonc`, `.assetsignore`), and point the legacy deploy at `legacy/wrangler.jsonc`. Check that `wrangler deploy --dry-run -c legacy/wrangler.jsonc` uploads the same files as before.
2. Add `package.json` (Node 24, ESM), `tsconfig.json`, `biome.json`, `vite.config.ts`, `react-router.config.ts`, `wrangler.jsonc` (`ashlanddailyhelp-app`, `nodejs_compat`), and `workers/app.ts` (the `fetch` handler, passing `env` to routes through a React Router context).
3. `app/root.tsx` (document shell, `lang`, viewport, one stylesheet), `app/routes.ts`, `app/routes/home.tsx` (a placeholder homepage, replaced by `10-homepage`) and `app/routes/health.ts` (JSON: app version and whether the database answers).
4. `server/db.ts`: open a Drizzle client from the Worker's env; `db/schema.ts` (empty until `06-ingest-feed`); `drizzle.config.ts`; `scripts/migrate.ts` to apply migrations to `DATABASE_URL`.
5. `test/db.ts`: a helper that creates a PGlite database with all migrations applied, for integration tests.
6. Tests first: the health route reports `database: "ok"` against PGlite and `"unavailable"` when the query fails; the homepage renders its heading; a Playwright journey loads `/` and `/health` from the built Worker.
7. `.github/workflows/deploy.yml`: a `check` job (Biome, `tsc`, Vitest, build), an `e2e` job (Playwright with a `postgres:17` service), `deploy-legacy` (as today, from `legacy/`), and `deploy-app`, which runs migrations and deploys only when the `DATABASE_URL` repository secret exists.
8. README: running locally (`npm install`, a local Postgres, `.dev.vars`, `npm run dev`, the steward's sample feed), the test commands, and the one-time production setup (Neon database, Hyperdrive or `DATABASE_URL`, `wrangler secret put`, GitHub secrets).
9. CLAUDE.md: record the choices above, and point the "Static site" sections at `legacy/`.

- Whether the Worker's Cloudflare account is the one shared with the steward can't be checked from here (wrangler isn't logged in locally, and the steward isn't hosted yet, steward issue #24).

- Moving the old site into `legacy/` makes the steward's checks of this repo's `core.js` and `data.js` (`fixtures/site-core`, `npm run demo -- --site`) skip or fail; `05-request-steward-decoupling` asks the steward to drop them.

Findings:

1. Fixed: the database connection closed when the handler returned, before React Router finished streaming the body. `server/request-database.ts` now closes it after the body has been sent, with tests.
2. Fixed: the production `DATABASE_URL` was visible to every step of `deploy-app`; now only the migration step sees it.
3. Fixed: a manual run could deploy, and migrate production, from any branch; deploys now require `main`.
4. Fixed: nothing checked the deployed app; `deploy-app` now fails unless `/health` reaches the database.
5. Fixed: an error opening the database (for example a malformed URL) escaped the health check's `try`; now reported as `unavailable`, with a test.
6. Fixed: `wrangler types` typed `DATABASE_URL` from the local `.dev.vars`, so types differed between machines and CI; it now skips env types (`--include-env=false`) and `workers/env.d.ts` declares them.
7. Fixed: the Worker's wiring had no tests and the route test helper used a double cast; the wiring moved to `server/request-database.ts` with tests, and `test/route.ts` builds real `LoaderFunctionArgs`.
8. Fixed: unused `@testing-library/user-event`, `preview` script, unused e2e database and a wrong Drizzle credentials fallback removed.
9. Fixed: an overstated comment about Hyperdrive pooling, and a workflow header that restated the jobs.
10. Fixed: README and CLAUDE.md inaccuracies (e2e needs a running database, the deploy gate is the repository secret, Hyperdrive precedence and `localConnectionString`, the steward isn't hosted yet, remaining static-site paths).
